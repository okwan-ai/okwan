# Threat model

**What is worth stealing:** a tenant's rail credentials (they read that
merchant's payments), the master key and database address (together,
every tenant's credentials), one tenant's reconciliation results, and
the ability to act as another tenant.

**Who might try:** any member of the public (signup is self-serve, so an
attacker can be a tenant), a tenant reaching for another tenant, a
malicious or compromised agent holding a legitimate key, someone with a
stolen key or session, and an insider with hosting access.

| # | Threat | Path | What stops it | Residual risk |
|---|---|---|---|---|
| T1 | One tenant reads another's data through the API | Any data route, any MCP tool, the admin routes | The tenant comes from the key or session hash only; subtree guard answering 404; `WHERE tenant_id`; row-level security | Low. Proven per surface and per wall; see controls C1–C6 |
| T2 | Caller SQL reads the server: files, environment, network | `POST /v1/query`, MCP `okwan_query` | DuckDB with external access off, extensions off, configuration locked; statement guard as a second wall | Low since 2026-11-03. Before that, open: [README](README.md), "Found while preparing this pack" |
| T3 | Caller SQL exhausts the one worker | A huge cross join, `range()` | Row limit on results; 1 MiB body cap | **Open.** No memory limit or timeout on a query; [known-gaps.md](known-gaps.md) G6 |
| T4 | Caller-chosen host reaches internal services (SSRF) | Postgres connector connection string | Egress guard: resolve, refuse non-public addresses, dial the checked address (`packages/core/okwan_core/egress.py`) | Low |
| T5 | Stolen API key | Leaked by the customer | Stored only as a hash; revocation is immediate; every read is recorded with the key's prefix and the caller's address and network, and a key on a new network or reading far above its usual hour alerts the account (C39, C40) | Medium: a stolen read key reads every connector until revoked (no per-connector scope, expiry or IP allowlist); it can no longer add merchants, issue keys or replace credentials (C44, T21); detection is by mail, within the hour for volume; G4, G17 |
| T6 | Stolen or guessed session | Cookie theft, password guessing | httpOnly, Secure, SameSite=Lax cookie; scrypt; sign-in limited per address and per IP; reset ends every session; a session ends after 30 minutes without use and 12 hours after sign-in (C37) | Medium: no second factor at customer sign-in; G3 |
| T7 | Account and tenant enumeration | Signup, sign-in, admin ids | Signup's answer never says whether an address is registered; one 429 message for every limit; a foreign tenant is 404 like a missing one | Low |
| T8 | Database dump or backup leaks | Neon compromise, a copied backup | Credentials are ciphertext under per-value keys; AAD stops moving ciphertext between tenants; tokens, keys and passwords are hashes | Medium: the master key sits in the API's environment, not a KMS; G1 |
| T9 | Verification or reset link intercepted | Mail provider, link tracking | Token single-use, 24-hour expiry, hashed at rest; tracking off; operator resets are out of band | Low |
| T10 | Writing to a rail | A connector operation that moves money | No reconciliation can be declared over a write operation (`validate_against_registry`); the SQL guard and sandbox allow reads only | Low. WhatsApp sends are mounted on REST; G8 |
| T11 | Response embedded, sniffed or cached | Framing, MIME sniffing, shared caches | DENY framing, nosniff, no-store, a locked policy on JSON, HSTS (`apps/api/okwan_api/edge.py`); dashboard headers (`apps/dashboard/next.config.ts`) | Low |
| T12 | Hosted MCP reached through DNS rebinding | A browser on a hostile page | Host and origin allowlist when `OKWAN_ALLOWED_HOSTS` is set | Low while set; it is set in production (`render.yaml`) |
| T13 | Insider or compromised hosting account | Render, Neon or GitHub access | Secrets only in provider settings and Codespaces; nothing secret in the repository | **Open.** Hosting access is full access, and no action log records what an operator did; G1, G2 |
| T14 | Dependency or CI supply chain | A malicious package or action | Python 3.12 pinned in the image; npm lockfiles; ruff pinned to a minor | Medium: Python dependencies are ranges with no lockfile; actions pinned by tag, not commit; no automated vulnerability scan; G9 |
| T16 | The support assistant is steered by what it reads | A customer's message, or text inside a tool result (a run error, a tenant name), telling the model to do something else | Every tool reads and runs as the caller through the subtree guard; the only write is a ticket; tool results are framed as data in the system prompt; the transcript is server-side, so earlier turns cannot be forged | Low: the worst a steered assistant can do is say something wrong or open a ticket. G13 |
| T17 | A secret reaches the model or its transcript | A customer pastes a key; a rail quotes one in an error | `redact` on every customer message and every tool result before the model or the database sees it; the customer is told to replace what was removed | Medium: pattern-based, so an unusual secret format can pass. G14 |
| T18 | Someone runs up the model bill | Scripted messages to the assistant | Rate limit per account (40 an hour) and per address (60); six tool rounds a message, twenty messages a conversation; the Anthropic console's spend limit | Low |
| T19 | Someone reaches the operator console | A stolen operator session, a customer probing `/v1/ops`, an API key | Allowlist on the sign-in address; a plain 404 for everyone else; an authenticator code per session for 30 minutes, single-use and rate limited; every action logged append-only | Low |
| T20 | Another website acts as the signed-in user, or reads what Okwan returns | A page the user visits sends requests to the API or the dashboard in the background | No CORS anywhere, so no response is readable cross-origin and no preflight passes; the API authenticates by header only and ignores cookies; the session cookie is SameSite=Lax, httpOnly, Secure; every dashboard handler that changes data requires the dashboard's own Origin (C42) | Low. No request-verification token on top of the Origin check: every changing request is JSON from the dashboard's own pages, and a request with no Origin is refused |
| T21 | A key given to an AI client or a reporting job is used to administer the account | The key sits in a plain-text client config, a laptop or a CI secret, and leaks | Keys are `read` or `admin`, stated where each is made; new keys are read-only unless admin is ticked or named; MCP setup only issues read keys; a read key is refused with 403 at every administration route, found from the app itself, so it cannot add a merchant, issue or revoke a key, replace a saved credential, delete an import or open support (C44) | Low for administration; a read key still reads every connector (G4). Keys from before this change keep admin until the customer replaces them |
| T22 | A stored credential is read back through a rail's error | A rail answers a request with an error that quotes the key it was sent ("Invalid API key provided: sk_live_…"), and a caller with any key reads that error | Cleaned where the error is made, before any surface (C45). Found by the red team on 2026-11-10: the data routes (connector REST, `/v1/query`, reconciliations, the hosted MCP's query tool) returned the rail's body as it came, while only the connection test and run history scrubbed it | Low: a value a rail encodes or transforms before quoting it (other than Basic) would not be recognised |
| T23 | A merchant's figures leave Okwan by mail | The daily check's mail goes through the mail provider to an inbox Okwan does not control | The mail holds merchant names, counts and totals only, never an order, a customer, a payment record or a secret; it goes to the account's own sign-in address and to no one else, not even the operator; the account can turn it off, and so can the link in the mail (C47) | Low: the provider and the inbox see that a named merchant has, say, two orders collected twice and the amount |
| T24 | The unsubscribe link is used by someone it was not sent to | A forwarded mail, a mail scanner that opens every link, or someone guessing tokens | The token can do one thing, turn that account's mail off, which anyone signed in undoes; opening the link changes nothing (a person presses a button, which posts); a token is 24 random bytes bound to one account id of a fixed shape, compared inside that account's database scope; guesses are limited per address and all refusals read the same (C47) | Low: whoever holds a forwarded mail can stop that account's mail |
| T25 | Okwan's own scheduled reads go wrong | A bug, a stuck rail or a database that cannot take a write makes the daily check read too often, run past a plan, or stall the server | Once a day per merchant, from the scheduler's own record, with the slot taken before any rail is read: a check that fails or cannot be stored is not due again until tomorrow, and if the slot cannot be written the round stops before reading anything; a check is a metered check and none runs past the account's plan; 200 checks or twenty minutes a round and five minutes a check at most; the operator can pause all of it with one setting (C46, C49) | Medium: one API instance runs one sweeper (G7), and a round runs in the API's own process, and a check's matching is bounded and off the event loop (C50), so a large merchant's check costs the API about a second of shared computing at most |
| T26 | Someone bends the daily check's schedule or its mail | An account fills every round with merchants whose saved keys are wrong, so no other account is checked; a key holder (a read-only key is enough) runs a merchant's check to put Okwan's off or to make its findings look already seen; a merchant's admin makes failed runs until an old finding looks new, or times checks so the account is mailed every hour | Accounts take turns within a round and the one served longest ago goes first; due, told and not-yet-mailed are the scheduler's own record, which no run from any other surface changes and which is not read back from stored runs; one mail a day an account (C46, C47). All four were proven by the attacker's pass of 2026-11-11 against the first version, before it was merged; a second pass on the rework led to a fifth, fifty runs with a read-only key pushing the run a waiting finding pointed to out of history, closed the same way | Low: an account with more due merchants than a round has turns is checked over several rounds; a finding found after the day's mail waits for tomorrow's (G18) |
| T27 | Text someone else chose is sent to the account as Okwan's own | A merchant-level admin names a tenant with line breaks, a lure and a link, or a would-be mail header; a merchant's store reports an order currency that is a sentence; both reached the mail's subject and body | A name is refused at creation unless it is one line (C48), and the mail shows any name as one bounded line with no control or invisible character, no address scheme and no joined-up address a mail client would make a link, never in the subject; an amount is shown only with a three-letter currency code (C47). Proven by the same pass; the bare address and the invisible characters by the second | Low: whoever can name a merchant still chooses up to sixty characters of one line of plain words in the account's mail, as they do in the dashboard, look-alike letters included |
| T28 | A tenant nested out of its account's sight | A merchant's admin key creates tenants beneath itself nine levels down, where the account cannot open the tenant and the plan lookup stops short of the account: the tenant was served on a plan of its own, and the first version of the daily check ran and mailed about it | The ninth level is refused at creation, and the daily check walks only as deep as the account can open and asks the account's own plan (C46, C48). Proven by the same pass | Low: a tenant made deeper before this rule would still be served on its own plan through the API; none is known in production, and the daily check does not reach it |
| T29 | A merchant shapes its own rows to exhaust the server | The rows a check reads are the merchant's own: thousands of payments sharing one reference, amount and hour; batches of nothing against a deposit no sum reaches; two dates at the ends of the calendar. Any key of that merchant, a read-only one included, then runs the check, as often as its plan allows; the daily check runs it unasked | Each fallback rule looks only at records that could pair and counts what it compares; past the bound it stops and says which records it did not reach; matching runs off the event loop (C50). Proven by the attacker's pass of 2026-11-11 for the fuzzy rule (fourteen seconds for two thousand rows a side); the group-sum rule, its search for a sum and the day-by-day lag were found while fixing it and measured the same way; an attacker's pass on the fix then proved two places it did not reach (a place to look made for every card on the other side; ten thousand records under one reference) and one fault of its own (below) | Low: a check over rows shaped this way still costs a second or two of computing each time it is run, inside that merchant's plan and rate limit, and a check cut off by a timeout goes on in its thread until that bound ends it; matching shares the interpreter with the API, so requests are answered meanwhile but more slowly; a query through SQL has its own limits (G6) |
| T30 | Okwan's own payments are taken back, or its payment account restricted, by disputes | A cardholder asks their bank to reverse a payment for Pro (not recognised, "I cancelled", "I was owed a refund"). The bank decides on what the seller can show; a seller with no published refund rule, or no proof the customer saw it, loses. Disputes also count against the account whether won or lost | The policy is published, drawn from the Terms, shown before payment in the dashboard and on Stripe's page, and what each Checkout session showed is recorded under that session, so the record of a payment is the record of the session that took it (C51) | Medium until the rest is built: nothing yet tells the operator a dispute has arrived or how the dispute rate is moving, and the evidence is put together by hand (OKWAN_PROJECT.md §10 item 40) |
| T31 | A customer who means to dispute a payment makes Okwan's evidence for it false or missing; or someone aims a payment or a record at an account that is not theirs | Open a second checkout after paying (from another network, or under a later policy) so the record describes a checkout that was never paid; open one with an API key so the record says a person saw what no person saw; pay through a Stripe payment link that names another account in `client_reference_id` | A record per Checkout session, written once and marked paid once; billing open only to the session's own account, never a key; a payment's account read only from Okwan's own metadata (C51, C52). Found by an attacker's pass before this was merged (red-team.md) | Low. The record is only as good as the address the dashboard reports for the caller (G17), and Stripe's own record of the session, which carries the policy's version in its metadata, is the second copy |
| T15 | Denial of service | Floods of requests | 1 MiB body cap; rate limits on signup, sign-in, verification and the connection test; monthly quotas | Medium: one instance, one worker, limits in memory per instance; no edge firewall in front of Render; G6, G7 |

## Assumptions

- Render, Neon, Vercel, Resend and GitHub operate their own controls as
  documented. Their compromise is out of scope except where noted (T8, T13).
- The rails authenticate and authorize their own APIs: a tenant's
  credential reads only what that rail lets it read.
- No surface accepts SQL against the vault database. Row-level security
  defends against a query bug in Okwan's code. It does not stop
  arbitrary SQL running as the login role, which could switch back from
  the restricted role. Nothing accepts such SQL today, and the
  restricted role cannot read the identity tables.
