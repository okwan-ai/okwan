# Known gaps

What is missing or weak, most serious first. Each has a plan; none is
hidden from the auditor. Closing them is tracked in `OKWAN_PROJECT.md` §10.

| # | Gap | Why it matters | Plan |
|---|---|---|---|
| G1 | **Master key in an environment variable.** Production seals credentials under `OKWAN_VAULT_MASTER_KEY` on the Render service. `KmsMasterKey` exists (`packages/vault/okwan_vault/keys.py`) but its client library is not a dependency, so it cannot run as deployed | Whoever reads the service's environment (Render access, or a hole like the one closed on 2026-11-03) can open every stored credential. There is no tool to re-wrap data keys under a new master key | Move to a KMS (the provider interface is already in place), and add a re-wrap command so the master key can be rotated without re-entering credentials |
| G2 | **No action log.** Credential changes, key issue and revoke, sign-ins, plan changes and operator commands are not recorded | An incident cannot be reconstructed, and an insider's actions leave no trace | An append-only table written in the same transaction as each action, readable per tenant; `OKWAN_PROJECT.md` §10 item 24. **Narrowed 2026-11-04:** the operator console records everything done in it, append-only (C33). **Narrowed 2026-11-09:** every read of a tenant's data is recorded with the key, the caller's address and what was read, for 90 days (C39); changes (credentials, keys, sign-ins, plans) are still not recorded |
| G3 | **No second factor at customer sign-in.** Idle timeout **closed 2026-11-04**: a session ends after 30 minutes without use and 12 hours after sign-in (C37) | A stolen password gives access until the session ends | TOTP for customer logins, as the operator console already has |
| G4 | **A key reads everything its tenant can.** Keys are read-only or admin (C44), and new keys are read-only, so a leaked agent key no longer administers; but a read key is not limited to one connector or table, has no expiry and no IP allowlist, and there is one login per tenant with no roles | A leaked agent key reads every connector its tenant has connected | Keys scoped to named connectors next (as Gusto scopes an app to `payrolls:read`), then members with roles |
| G5 | **No purge of expired rows.** Expired sessions and signups, revoked keys and old usage stay until deleted; account deletion on request exists (`tenant delete`, 2026-11-04) | Holds data longer than needed; expired rows are kept past their use | A scheduled purge, and an operator `tenant delete` that cascades, with a written retention policy (owner and counsel, [owner-and-legal.md](owner-and-legal.md)) |
| G6 | **A query has no memory limit or timeout.** One uvicorn worker serves everyone | One expensive query from one tenant slows or stops every tenant | DuckDB `memory_limit` and `threads` in the sandbox, and a wall-clock limit on query execution |
| G7 | **Single instance, limits in memory, no edge firewall in front of Render** | A restart resets rate limits and drops Gusto connections in progress (the admin connects again). The daily check's sweeper also assumes one instance: two would each run a due merchant's check. Gusto's token renewal is serialised by a lock in the process: a second instance would need it in the database, or two instances could spend one refresh token twice and disconnect the business; one instance is one failure; floods reach the app. The limiter bounds each rule on its own: a flood of fresh subjects on one rule (a new address on every request) makes room among that rule's own counters, its expired ones and then its oldest, so a per-address rule can be made to forget an address while every other rule's counters are kept (the attacker's pass of 2026-11-22, finding 9). What must survive a restart or a flood, the day's model calls for suggestions, is counted in the database; that one suggestion is made on an item at a time is held in the process, as one instance | A second instance once there is traffic, with limits in the database or a shared cache; Render or a CDN in front for volumetric protection |
| G8 | **WhatsApp send operations are mounted on hosted REST** | The only write operations an API key can call. Not a payment rail, but a key holder can send messages from the tenant's WhatsApp number | Unmount non-read operations from hosted REST, or keep them behind a scope (G4); `OKWAN_PROJECT.md` §10 item 23 |
| G9 | **Supply chain.** Python dependencies are ranges with no lockfile; GitHub Actions are pinned by tag, not commit; no automated vulnerability scan | A compromised release or retagged action runs in the build or CI | A lockfile for the image (`pip-compile` or `uv lock`), actions pinned to commits, `pip-audit` and `npm audit` in CI |
| G10 | **A rail's 401 passes through as Okwan's 401** | A customer reads "unauthorized" and suspects their Okwan key when their Stripe key is wrong | Map upstream auth failures to a distinct status or error code |
| G11 | **No backup restore has been tested.** Neon keeps point-in-time history according to its plan; nobody has restored from it | A backup never restored is a hope | A restore drill into a branch, written into the runbook |
| G13 | **The support assistant can be wrong.** It answers from Okwan's documentation and the account's own data, but a model can misread either | A customer acts on a wrong instruction. It cannot change anything itself, and it says it is an AI | Escalation on anything unresolved; every conversation kept 30 days for review; customer reports of wrong answers treated as bugs (runbook, "Support assistant") |
| G14 | **Secret redaction is pattern-based.** Okwan's own tokens, the rails' key formats, connection-string passwords and long opaque tokens are caught; a short password typed in prose is not | A customer's password reaches the model and the transcript | Tell customers in the panel never to paste secrets (it does); widen the patterns as formats are seen |
| G15 | **One person behind the assistant.** Tier 1 is automated; everything it escalates reaches one person | An escalation waits while that person is away | A second on-call engineer (owner decision, runbook "Owner decisions") |
| G16 | **The console's second factor is one authenticator app.** There are no recovery codes, and the operator log is readable only by operators and the database owner | A lost phone locks the owner out of the console until they re-enroll from the Codespace | Recovery is re-running `python -m okwan_vault operator enroll`, which needs the vault master key; a hardware key later |
| G17 | **The caller's address is Cloudflare's word for it.** The access log and the rate limits read the address from `CF-Connecting-IP`, which Cloudflare overwrites. A request sent straight to `okwan.onrender.com`, around Cloudflare, can set that header itself. The same address is what a checkout's record holds and what the answer to a disputed payment gives as "where they paid from": the answer says where the address comes from and does not vouch for it | Such a caller can be logged under an address of its choosing and dodge a per-address limit. It still needs a valid key, and is logged under that key | Accept requests only through Cloudflare (Authenticated Origin Pulls, or a secret header Cloudflare adds and the API checks), or retire the `onrender.com` host for the API |
| G18 | **An item can wait a day or more for its mail.** An account is mailed once a day at most, so an item found after that day's mail is in the next day's; a mail names 25 merchants at most, those told longest ago first, and the others' news waits for the next. One look reads at most 100,000 items or 2,000 merchants and the next goes on from there, so an account larger than that is read over several rounds, and a merchant read after the day's mail waits for the next day's. A check keeps its 1,000 worst rows: the mail tells apart only those, and counts the rest as found ("Open items counts them") | An item can be a day old, or older for an account with more than 25 merchants with news or more than a look reads, before a mail says so; it is on Open items at once | Group an account's merchants into one daily slot, so the day's checks and the day's mail fall together |
| G20 | **What the answer to a disputed payment cannot show.** Two limits the answer states rather than hides. The record of an account's requests is kept 90 days and a cardholder has about 120 to dispute: for a payment older than 90 days the use made straight after paying is gone, and the answer says from when the record speaks. And a payment is Okwan's by its Stripe customer, because Stripe sends nothing with a charge that names the product: if another product on the company's Stripe account charged a Stripe customer Okwan knows, that charge would be listed as Okwan's, in the rate and with Okwan's evidence beside it, marked only by a note when it is not the price of Pro | A customer who waits past day 90 removes the best evidence against "not received" and "not authorised"; a person has to check a noted payment in Stripe before answering for it | Keep a count of requests per paid month with the payment, written when the month ends, so the fact of use outlives the log without keeping addresses longer; and put Okwan on a Stripe account of its own, or read the charge's invoice from Stripe to see its price |
| G21 | **A reference in an imported file is kept as the file has it.** A batch id or a statement reference is up to 200 characters of a merchant's own text, and the importer keeps every character, among them ones that draw nothing (a zero-width space, a variation selector, a filler) or turn the text around them. The Files tab draws a reference whole, apart from its own sentences, and spells such characters out (C55). REST, SQL and MCP return the reference as written, which is right for data and leaves the drawing to whoever shows it. Two limits remain on the tab itself: two ids that differ only by look-alike letters of different alphabets cannot be told apart by eye, and a reference stacked with combining marks has not been tested for drawing over the lines beside it | A merchant, or whoever prepares a merchant's file, can make two batches look like one to a person reading a result, or make an id read as a sentence in a tool that draws it inline; an agent reading a result through MCP receives the text as it is | With a first ISV's real files in hand: have the importer say, at mapping time, which rows carry such characters in a reference column, and refuse or strip them by the owner's decision; say in the MCP tool's description that references are a merchant's text |
| G22 | **A server-drawn page can be thrown away and drawn again on a slow link.** A page reaches the browser in pieces. Where a page is drawn on the server, a part of it can be sent in a later piece than the element that holds it; on a slow link the browser takes that element over before its inside has arrived, takes it again when it has, and React discards the server's page and draws it again in the browser ("hydration failed"). The words on the page are the same afterwards. The Files tab did this one load in seven at 400 kbit/s and is now drawn from data, like the Findings and Connections tabs, which cannot (C55). Overview, Settings and the cross-merchant Findings page are still drawn on the server in parts. None of them has done it since: on 21 November every signed-in page (19) was loaded 20 times through a slowed document and Overview, Findings and the five Settings tabs 60 times each on a fast link, and none of 800 loads threw. One layout-check run in thirteen did see Settings do it on a fast link, before then, and later on 21 November one run saw the Integrations page do it once at 390 px; neither has been reproduced on demand | A person on a slow connection sees the page flash and an error in the browser's console; nothing wrong is shown. The layout check prints such a page instead of failing on it, so that a required job does not fail at random | Draw the remaining server-drawn pages so that nothing can arrive after what holds it (from data, as the three tabs are, or with each late part in a boundary of its own), then load every page through the slowed document in the layout check and fail on any that throws |
| G23 | **An open item's age starts again when the merchant's files change, and an item older than its check's lookback leaves the list.** Open items are read from stored runs and hold nothing of their own. Deleting or the expiry of any of a merchant's imported files deletes every stored result that read that merchant's files, as the privacy policy says, so the next run starts their findings' ages again; the most common case is a 13-month-old file expiring. And a check reads only its lookback: a batch never paid stops being read once its day leaves the window, and with it leaves the list, while a deposit near the edge can be listed as one no batch explains (the attacker's pass of 2026-11-21, findings F4 and F11) | A person can see an item's age fall to zero, or an old unpaid batch disappear, with nothing done about it | For the owner: narrowing the privacy policy to "a result goes with the files it read" would keep a result whose files are all still there. In the code: a person's decisions on an item are kept in a table of their own (C58) and are not reset when the item's age is, but an item still leaves the list with its run; a decision on a check that reads files goes with the files, as its result does. Keeping an item past the lookback, open until a person closes it, is §10 item 43 |
| G24 | **The newest runs of an account's merchants are read whole, with no limit.** `GET /v1/tenants/{id}/runs/latest`, which Overview and Findings read, returns the newest run of a check for the target and every direct child with all of its rows, unpaged and with no rate limit: about 41 MB for 150 merchants in-process, and on Postgres each statement is weighed against every merchant id of the account (the second attacker's pass of 2026-11-21) | An account with many merchants makes those pages slow and holds memory on the API while they load | Page it by merchant as the open-items list is (50 a page), and read rows only for the merchants a page shows |
| G25 | **A decision made as a check's new run is being stored counts from the run after.** A run's summary leaves out the items closed when it is stored, and the account's list adds the decisions made since, against that run, by its id. A decision recorded against the run before, in the moment between the new run reading the decisions and being stored, is in neither; so is one recorded against the run before while the decide route itself was reading it, if the new run was stored in that moment (the second pass). The item leaves the list at once and, when it is among the 20 the summary keeps, the count with it; past those 20, the check's open count holds it until the next run, and if it is opened again before then the count is one too low (an item among the 20 is counted right either way: the attacker's pass of 2026-11-21, finding 5). The merchant's own list, which reads the rows, is exact. And a note is the person's own words: Okwan checks it can be read as it shows, not that it is true | An account's count can be one too high for a day | Count a decision against whichever run is newest when it is read, not when it was made, once the daily mail (§10 item 43 step 4) reads the same counts |
| G26 | **Two findings alike in every reference and day cannot be decided.** A finding's key is made from what it is about; two alike in every part (two terminals that each closed batch 001 that day, a bank that repeats a reference on two credits) are told apart only by the order a run lists them in, which can change from one run to the next, so a decision could follow the key to the other one (the attacker's pass of 2026-11-21, finding 1). Such twins are listed, with their amounts, a decision on either is refused, and a decision made on one before the other appeared no longer closes it (the second pass, finding 4) | Two such items stay on the list until a run no longer finds them both | Key a finding by what tells twins apart when the file has it (a terminal or merchant id on a batch, a bank's own transaction id), so each can be decided |
| G27 | **A closed item past a run's cut is counted open.** A run keeps at most 1,000 rows, findings first; a finding past the cut has no row, so no key to hold a person's decision to, and the check's open count holds it while its history says it was explained (the attacker's second pass of 2026-11-21, finding 8). The check says its rows were cut, and the dashboard says that its counts may include items someone closed | An account with more than 1,000 findings in one check, some explained, sees an open count too high by those past the cut | Keep the rows of items a person decided ahead of the cut when a run is stored |
| G28 | **A suggestion's note is the model's words.** Okwan checks that a suggestion cites only records it was given, and shows and keeps each cited record as it stored it, so the evidence beside a suggestion is Okwan's own. The note is the model's: a figure or a day in it is not checked against the records, and it can be wrong while its evidence is right. It is shown as a suggestion, beside those records, and nothing comes of it until a person decides; the person's decision says whether they kept its words, and a decision made in Okwan's words is never shown back to the model as a person's practice. The day's allowances are read before a call is metered, so calls made at the same moment can each pass and together go a few past them; each caller's hourly limit bounds by how much. A model call counts as one request on the plan, the same as a run (`apps/api/okwan_api/suggestions.py`) |
| G29 | **An item that falls past a stored result's cut and comes back is first seen again.** A stored result keeps a check's 1,000 worst rows; a finding pushed past them by worse ones has no row, and when it is back among them its first-seen time starts again, so Open items shows it as first seen then, and the daily mail tells of it as new once more (the attacker's pass of 2026-11-23, finding 6). The merchant's own records decide this, and only for that merchant's own items: the account is told, again, of an item that is open | A merchant with more than 1,000 findings in one check can see an item mailed as new twice | Keep, per check, the keys of findings past the cut with their first-seen times |
| G30 | **What an agent reads, an agent may act on elsewhere.** The open items hold references from the merchant's systems, owners and notes people wrote, and suggestion notes a model wrote over the same records. Okwan returns them as data, says so in the tool, and lets no key used there decide anything; it cannot stop an agent the account connected from treating a note as an instruction somewhere Okwan does not reach. One read covers 20,000 items (and the merchant it is reading when it gets there) or 2,000 merchants at most, and says how many merchants it left out; one merchant can be read on its own (`apps/api/okwan_api/open_items.py`) | An agent given a read key can be told something by a note a colleague wrote | Mark each text field with who wrote it, so an agent can weigh it |
| G31 | **What an address is told, and when.** An address hears of what changes after it is added; what is already open is read with `GET /v1/exceptions`. An event can come twice and in any order (at least once): a receiver tells them apart by the item and the type. `aged` is said by a run that finds the item still open, so a merchant whose checks stop running is not said to age. An address turned off, and on again, is not sent what was made meanwhile; `GET /v1/events` holds it for 30 days. One secret an address: rotating it is adding a new address and deleting the old one. Addresses are managed through the API only until the dashboard step (`apps/api/okwan_api/webhooks.py`) | A receiver that treats events as exactly once, in order, double-counts | A second secret during rotation; the dashboard screen |
| G12 | **No penetration test, no SOC 2.** This pack and its tests are the evidence today | Larger customers will ask for both | The owner's choice of firm and timing ([owner-and-legal.md](owner-and-legal.md)) |
